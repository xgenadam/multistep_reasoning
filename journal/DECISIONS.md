## D-001 — One door: every store sits behind `ContextStore`    2026-10-13 · S-001 · active
Decision: The model never loads a corpus; it explores stores (the `Document` first, then corpora, notes, chat turns) through one bounded `ContextStore` interface the oracle queries. Phase A adds zero runtime deps and zero services, and adds `context/` beside the existing layout with no package-rename commit (plan D-Q).
Why: Corpus unbounded, window bounded. Interface mistakes must surface in days against `Document` alone, before any backend exists; a rename breaks the extension's imports and every test import for no Phase A value.
Supersedes: none (PLAN v1 Phase A item 1 "pure rename commit")    Re-open if: A-4 fails, or a second store cannot be added without changing the interface.

## D-002 — Faces: oobabooga extension for chat, `jobs` CLI for long runs; MCP retired    2026-10-18 · S-004 · active
Decision: `reasoning_sub_agents` stays platform-agnostic behind two thin faces: the oobabooga extension (chat turns, harness-as-tool) and a headless `jobs` CLI (Phase R) for multi-hour runs. The MCP server stays retired (schema in `archive/mcp-deep-reason-schema.md`). (plan D-G)
Why: Multi-hour jobs cannot be driven from a chat UI; the baseline harness is already half a headless driver.
Supersedes: none (PLAN v1 "oobabooga extension only")    Re-open if: a third client needs the harness and neither face can serve it.

## D-003 — Storage: SQLite FTS5 lexical, vector backend chosen at B-02, no Neo4j    2026-10-18 · S-004 · active
Decision: Lexical retrieval is SQLite FTS5 (stdlib). The dense backend and embedding service are chosen at B-02 by a 1 M-chunk benchmark on the real box. Graphs are in-process (sqlite adjacency over a persisted edge list); no Neo4j. (plan D-A)
Why: Nothing pre-B needs vectors; the choice depends on measured throughput on a box shared with a 27B/123B generator.
Supersedes: none (PLAN v1 "server-based Qdrant or Chroma")    Re-open if: B-02's benchmark shows no candidate meets B-3, or graph queries outgrow sqlite.

## D-004 — Corpora: a framework with per-source adapters, papers first; write side later    2026-10-18 · S-004 · active
Decision: Phase B is a corpus framework (parse → structure-aware chunks → lexical + dense index → typed edges; resumable, incremental ingest) with per-source adapters, starting with `papers` at tier 1. Wiki/books/code adapters, the KB write side (derived notes with provenance; notes never outrank sources) and scale tiers 2–4 are later phases with their own gates. (plan D-H, D-I)
Why: Papers, wiki pages and books need the same pipeline; the citation/link/canon graph generalises the call graph. Scale must be proven by tiers, not assumed.
Supersedes: none (PLAN v1 Phase B "tree-sitter + call graph", read-only KB)    Re-open if: the papers adapter needs framework changes that a second adapter would not share.

## D-006 — Durable runs: persisted, resumable, bounded two-level milestone loop    2026-10-18 · S-004 · active
Decision: Every long run persists under `/runs/<run_id>/` and resumes after a kill. Reach comes from a bounded two-level loop (plan/outline → milestones, each milestone one pipeline turn against shared stores) with explicit budgets, not recursive self-decomposition. (plan D-F)
Why: A book or a 200-paper review is hours to days of calls; flat decomposition does not reach that scale and unbounded recursion is budget-unstable.
Supersedes: none    Re-open if: R-1 or R-6 cannot be met with two levels.

## D-007 — Gates: marginal cost on uncontaminated runs, and quality by judge    2026-10-18 · S-004 · active (quality half superseded by D-019)
Decision: Cost gates measure the marginal cost of the pass under test (its calls plus the calls it triggers) ÷ the turn total, only on uncontaminated runs (`compare.py` refuses `jobs > 1` or an inflated compose p50), against a baseline re-recorded whenever prompts change materially. From Phase Q on, quality is a gate too: pairwise judge, n ≥ 10. (plan D-O, D-E)
Why: Turn totals vary 36K–305K tokens across identical scenarios, and the Phase 0 prompt changes grew tokens 3–5× unnoticed (N18). Cost-only gates cannot tell whether the harness helps.
Supersedes: none (P0-4's "turn totals B vs A", cost-only gates)    Re-open if: a marginal measure cannot be attributed (labels unreliable) or judge repeatability fails Q-5.

## D-009 — Execution model: conservative-biased DAG, serial compose, serial recovery    2026-10-13 · S-001 · active
Decision: Sub-tasks form a DAG whose decompose prompt emits an edge whenever unsure; frontiers run in parallel against a frozen snapshot while compose stays serial and must reconcile overlapping siblings; a verifier-flagged, context-starved sub-task is re-run serially with its siblings' outputs, not merely detected.
Why: A wrong sequential edge costs one slot of latency; a wrong parallel edge costs a blind sub-task. Detection without recovery is a dead end.
Supersedes: none    Re-open if: P-P4 shows serial recovery cannot repair a missing edge.

## D-010 — Packs are config bundles with a layered `VerifierSpec`    2026-10-13 · S-001 · active
Decision: A domain pack is configuration (prompts, tools, stores, verifiers, output shape), not core code. `VerifierSpec` is layered (objective hook / LLM judge / opt-in FOL), and every verdict carries a confidence tier: objective pass > judge-agree > judge-unsure → annotation.
Why: Code verifiers are objective; book, legal and science verifiers are a different mechanism, and proving the contract with `code` alone would hide that.
Supersedes: none    Re-open if: T-2 fails (a pack needs core code changes to load).

## D-013 — Model thinking is explicit, off for baselines, logged out of band    2026-10-19 · S-007 · active
Decision: Every call sends an explicit thinking switch (`extra_body={'chat_template_kwargs': {'enable_thinking': …}}`), set by `options.thinking` (`off` | `on`) with optional per-step overrides; the default and the 0-16 baseline are `off`, and `on` is measured as its own comparison. Reasoning text (`reasoning` / `reasoning_content`, or a leading `<think>…</think>` stripped from content) is never fed into the Document, summary or any prompt. It goes to a side log: JSONL under `/runs/thinking/` (ignored), with per-call `reasoning_tokens` and a capped excerpt in harness run files. Run files record the thinking setting.
Why: The code never set thinking, so runs took the server's default: `:8091` vLLM thinks only when asked, and `:5000`'s setting at S-002 is unknown. Thinking tokens count in `completion_tokens` and move cost and wall time, so an unrecorded default confounds every baseline. Keeping it out of the context honours "window bounded"; logging it keeps it debuggable.
Supersedes: none    Re-open if: `on` beats `off` on Q-gated quality at acceptable marginal cost, or a step needs its own reasoning carried forward.

## D-017 — File-part bodies are unwrapped in code at apply time, not by prompt    2026-10-19 · S-015 · active
Decision: `resolve_body` strips one outer code fence from any body landing in a `file` part (`unwrap_outer_fence`). It strips only a true wrapper: the first line opens a fence, the last line closes it, and no line in between closes it under CommonMark rules. Anything else is kept as is. `render()` is unchanged, and `assert_payload_kept` accepts the unwrapped payload. COMPOSE_PROMPT rule 7 stays as written.
Why: 0-09's prompt-only fix could not work. Rule 1 has the composer copy the executor's reply with `body_source="current_result"`, and that reply is markdown with a fence the composer never sees or types. Every post-fix failure (7 of 7 bodies) was a clean whole-body wrapper. Stripping at copy-in, with the strict closing rule, avoids the risk the ticket raised against `render()` stripping (a README with inner fences).
Supersedes: 0-09 Notes' "fix of record: prompt-side"    Re-open if: a run shows a file body with a wrapper plus trailing commentary (the unwrap leaves it, and rule 7 alone has to handle it), or a legitimate file whose whole content is one fenced block (e.g. a one-snippet .md).

## D-018 — ContextStore v1 is tiers, roles on parts and working memory as a store    2026-10-19 · S-017 · active
Decision: The `ContextStore` protocol is `journal/design/A-01-context-store.md` § 1 (`describe`, `list`, `read`, `search`, `ask`, `summary`; `write` reserved; `Hit` with a required store id and per-kind provenance). Every store instance has a tier, `working` > `conversation` > `corpus` > `derived`; the oracle merges hits by tier then rank, never by raw score, never drops a tier's hits, and `Answer` carries `citations` built only from retrieved hits, `conflicts` and `unresolved`. A tool call with no `store` searches the working tier, but every store in scope is listed to the model, which decides whether to search and escalates by tier when unsure. The tier order is the provisional default: context-dependent precedence, confidence-driven search depth and escalating a conflict into a fresh reasoning run are designed in A-06 before anything implements them. Replies, artifacts and working memory are not separate documents: `Part.role` in {`artifact`, `reply`, `scratch`} (default `artifact`) on the one `Document`, landing with A-04, plus a pipeline-written `results` store of sub-task results, landing with A-03. The rolling summary stays in-prompt. Phase V gains V-5 (a planted conflict is surfaced 3/3). (user-approved, S-017)
Why: one id space keeps citations and D-014's identity rule meaningful across roles; three documents would change the op union, snapshots, the harness and the compose prompt for no Phase A value; the s3 op logs show the model needs working memory it can read, which a pipeline-written store gives at zero prompt cost. Scores are not comparable across backends, so cross-store order must be rank-based. A fixed precedence is wrong in general (a book's draft deliberately diverges from canon; a research assumption can be overturned by a source), so the order is a default, not a rule.
Supersedes: none (answers the question D-014 left to A-01)    Re-open if: V-1 needs an interface change for the papers store; the role split fails P0-3 or a Q gate once the composer sets roles; or A-06's approved design changes the precedence or escalation rules.

## D-019 — Quality claims are pre-registered, powered and compute-matched; Q precedes A's implementation    2026-10-19 · S-018 · active (self-judging clause superseded by D-021)
Decision: A pass that claims a quality gain shows a Wilson 95 % CI lower bound above 0.5 on decisive pairs and a point estimate at or above the effect pre-registered in the ticket's Notes before its first run file (default 0.70). The primary comparison is the harness against a self-refine single-model arm matched on completion tokens (±25 %); bare single calls, thinking off and on, are secondary. Objective checks score what they can (hidden tests for code, checklists for reports) and the judge scores the rest; no judge verdict replaces a test result, and domains are never pooled. G3 non-inferiority (Q-03's thresholds) stays for changes that claim no gain and runs on the standing `g3` subset from A-05 on. The benchmark is a frozen, versioned set under `journal/baseline/bench/`, ≥ ⅓ long prompts (deliverable beyond one call's `max_tokens`, or multi-file) and ≥ 20 % follow-ups; single-model arms continue until done. Judging is pairwise, both orders, decisive only when both agree, on two tiers (fast co-resident, slow sequential) with judges chosen by Q-04 and self-judging as control and fallback (its caveat: self-preference is symmetric across arms, shared blind spots are not, and the damaged pairs test those; it is never the judge of record once a cross-family judge passes Q-1 in that tier); one judge per table; every verdict records judge, rubric version and commit. Every arm driver and every judge call records wall-clock time per call, per prompt and per arm under the contamination rule (AGENTS.md § Measurement), reported beside quality and tokens. Q-01, Q-04 (slow tier), Q-02 and Q-03 run before A-02 starts; A-02's session may overlap Q-02's campaign window with the campaign on a pinned worktree; the Q-E1 verdict is the re-plan point before A-03. (user-approved with the wall-clock addendum, S-018)
Why: n ≥ 10 cannot separate 0.70 from chance (7/10 gives 0.40–0.89); a bare single call uses a fraction of the harness's compute, so "the harness wins" could mean "more compute wins"; code can be tested; short tasks are where the harness is least likely to help; A through T invest in the pipeline, and D-007 already makes quality a gate from Q on, which needs the gate before A lands code. The judge is a model swap on this hardware (one large model at a time), so judging is scheduled and budgeted, not free.
Supersedes: D-007's quality half ("pairwise judge, n ≥ 10"); PLAN's S-012 proposal block.    Re-open if: the measured judge budget (Q-4) makes the powered n infeasible on the generator and the slow-tier judge; or (a″) cannot be matched within ±25 % on completion tokens; or Q-04 finds no judge that passes Q-1 in either tier.

## D-021 — Flash-next is the judge of record; a cross-family judge must concur on every primary claim    2026-10-23 · S-021 · active
Decision: Flash-next (`qwen3.8-flash-next`, thinking off) judges every Q-E1 table, on all three generators. Devstral-2-123B Q3_K_M (llama.cpp, tensor split) is the concurrence judge: it judges the primary comparison, (b) against (a″), on every generator. A quality claim passes only if flash-next's verdicts meet D-019's bar (Wilson lower bound above 0.5 and the pre-registered point estimate) **and** Devstral's decisive win rate on the same pairs favours the same arm; the two judges' agreement rate is reported beside every table. Objective checks still score first (D-019); the judges score only what tests and checklists cannot. This is conditional on flash-next passing Q-1's real-pair half (≥ 4/5 on the R1–R5 labels); until then it is provisional, and if flash-next fails it, Devstral becomes the judge of record with flash-next as the concurrence judge. Cost per call (p50, Q-04): flash-next 2.5–3.1 s, Devstral 13.1 s (tensor split); the concurrence pass is 3 generators × 80 prompts × 2 orders = 480 calls, ≈ 1.7 h. (user-approved 2026-10-23)
Why: Q-04 measured flash-next as the most accurate judge on the standard slice (0.92, Wilson 0.86–0.96, against 0.72–0.83 for every cross-family candidate, on pairs it did not write) and the most position-consistent on the bespoke set (0.92). Every Q-E1 comparison is within one generator, so self- and family-preference fall on both arms alike (D-020). What remains is shared blind spots: harness errors flash-next cannot see would inflate the harness's score; the concurrence judge from another family catches that. A judge weaker than the strongest generator it grades (Devstral, 0.80) would cost more accuracy than self-judging's residual bias. Requiring both judges to agree makes a false "the harness helps" less likely, at the price of failing borderline gains.
Supersedes: D-019's clause "it is never the judge of record once a cross-family judge passes Q-1 in that tier"; D-020's sentence "One judge of record (Q-04's slow-tier pick) judges every table; flash-next's verdicts on the two other generators' tables are a second opinion, never the verdict of record."    Re-open if: flash-next fails the R1–R5 labels; Devstral's direction disagrees with flash-next's on any generator's primary comparison (the claim then fails, and the disagreement is examined before the next campaign); or a judge from another family scores at or above flash-next on the standard slice.

## D-024 — Every intermediate output is stored and scored; self-refine gets a 3× hard ceiling; the harness gets an off-by-default token ceiling    2026-10-24 · S-022 · active
Decision: From before Q-02 stage 1, the following holds. (the user's instructions, 2026-10-24)
- **Intermediates are kept.** Each harness turn's plan (the decomposer's sub-tasks and its history: initial plan, critique, regenerations) and its Document after every sub-task are written by `TaskOrchestrator.on_step`. They go to `intermediates/<run stem>/<turn id>/` at the repo root: git-ignored, on the large HDD, with a manifest whose hash the run file records. Self-refine's rounds stay in the run file (D-023), each with its completion tokens. Both are logging only.
- **Every intermediate is scored** (`intermediates.py score`): hidden tests for code, checklists for reports. The **most recent** complete output is what an arm delivers and what the pre-registered comparison scores. The **best** intermediate is reported beside it as an oracle upper bound, since it is chosen with the hidden tests or checklist, never as an arm's output.
