## What went right

- The harness design paid off immediately: one instrumentation point
  (`chat.completions.create`), serial runs for uncontested latency,
  per-turn JSON pairing time with output. The whole pipeline's behavior is
  now inspectable without touching oobabooga.
- The first full run surfaced **two real defects** the code audit missed:
  the server's ~2804-token generation cap (truncates JSON completions →
  `IncompleteOutputException`) and the missing `Document.from_dict()`
  (crashes any multi-turn continuation). Both are now tickets (cap →
  harness-side `max_tokens=8192` with a caveat; from_dict → 0-08).
- P0-5 core (golden-fixture parser tests) is 23/23 green — the
  baseline's regression half is recorded before any Phase 0 behavior
  change lands.
- Found the repo's `.gitignore` blanket-ignores `*.md`, which would have
  kept the entire journal (the audit trail) out of git; fixed with
  `!journal/**/*.md`. Commit `5795be0`.

## What went wrong

- Two smoke attempts before the real run: (1) `IncompleteOutputException`
  — chased to the server's generation cap via a bare `curl` probe;
  (2) the s3 multi-turn crash — the harness passed `to_dict()` output
  straight into `Document(**…)`, which accepted dicts and blew up in
  `outline()`. Neither was the harness's fault only: the pipeline has no
  snapshot-reconstruction path (0-08).
- The harness's first `run_scenario` created a second, uninstrumented
  client — caught by review before the real run (would have silently
  produced zero measurements).
- P0-2's first check was written against part count; the report scenario
  legitimately collapses to one part with in-body `##` headings. The
  criterion is about *rendered* sectioning, so the check now counts body
  `##` headings too. The baseline result still fails: s2 produced **zero**
  `##` headings in a single 2.7K-char part — a flat wall of text where the
  prompt asked for "clear section headings". Real D2-adjacent evidence.

## Pain points and how they were solved

| Pain | Cause | Resolution | Left a durable fix? |
| --- | --- | --- | --- |
| GPU busy but no visible agent activity | Baseline runs are long (10–11 min/turn) and silent except at the end | Run as background job; job notifications replace polling | Yes — harness is job-shaped by design |
| JSON completions truncated | Server default cap ≈ 2804 completion tokens (`finish_reason: length`) | Harness sets `max_tokens=8192` on every call (server honors it) | Harness-side; pipeline-side fix is a Phase 0+/A concern |
| Multi-turn continuation crashes | No `Document.from_dict()`; `Document(**to_dict())` yields dict parts | Harness rehydrates with `Part.model_validate` / `AppliedOp.model_validate` | Ticket 0-08 adds `from_dict()` |
| Test suite doesn't collect | Dead imports (`chat_adapter` moved, `mcp_server` retired) | Fixed chat_adapter import path; deleted `test_mcp_server.py` loudly | Yes (0-07 note) |
| `.gitignore` hides the journal | Repo-wide `*.md` ignore from before the journal existed | `!journal/**/*.md` | Yes, committed |

## Decisions made

- **Baseline = 4 scenarios × 2 runs, serial (`jobs=1`), uncontested.**
  s1 CLI (P0-1), s2 report (P0-2), s3 multi-turn overlap (P0-3),
  s4 multi-sub-task anchor (P0-4). `--jobs N` exists for later
  throughput experiments on the 5-slot server.
- Harness `max_tokens=8192` is part of the baseline conditions: a pipeline
  truncated at 2.8K tokens is not the pipeline we'll ship.
- P0-2 pass = rendered sectioning (section parts **or** body `##`
  headings ≥ 2), not part-count granularity.
- Repo-local git identity set to `DSH Agent (ubuntu) <dsh-agent@localhost>`
  so ticket commits work in-container; user may override later.
- 0-08 added: `from_dict()` + the 8 pre-existing test failures get a
  ticket instead of being silently folded into 0-07.
