I am the principal engineer at Basketly, an online grocery and household-goods retailer. Our whole business runs on one monolithic web application, and it has become the main thing slowing us down. The CTO has approved a gradual move to services, and I have been asked to write the migration guide that every engineering team will follow over the next 18 months. Please write it, about 7,500 words.

The readers are the 60 engineers in our nine product teams, plus their managers. They know the monolith well but most have not done a migration like this. Be practical and specific to our system: concrete steps, the order of work, what can go wrong and how we will know. Stay vendor-neutral: describe infrastructure by what it is (a message broker, a container platform, a relational database), and do not name any cloud provider or commercial product.

**The current monolith.**
- One Python web application (about 640,000 lines of code) with one PostgreSQL database of 212 tables. Several modules read and write each other's tables directly.
- It runs as 14 identical instances behind a load balancer. A full deploy takes 38 minutes, and we deploy twice a week, with a release freeze in the four weeks before Christmas.
- Peak traffic is 2,300 requests per second, on Saturday mornings. Checkout's p95 latency at peak is 1.9 seconds.
- Background work (emails, stock updates, search indexing) runs in a job queue inside the same codebase.
- The test suite takes 52 minutes and is flaky: about 1 run in 6 fails for reasons unrelated to the change.

**The eight target services, extracted in this order:**
1. Notifications (email, SMS and push messages)
2. Search (product search and autocomplete)
3. Catalog (products, categories, prices)
4. Inventory (stock levels per warehouse, reservations)
5. Cart
6. Orders (order history, status, returns)
7. Payments (payment provider integration, refunds)
8. Checkout (orchestrates cart, inventory reservation, payment and order creation)

**Decisions already made.** We use the strangler-fig pattern: a routing layer in front of the monolith sends traffic for an extracted capability to the new service, one capability at a time. Each service owns its data, and no service reads another service's tables. Data is synchronised during migration with change data capture from the monolith's database and the transactional outbox pattern in new services; application code must not write the same data to two databases (no dual writes). Services communicate through synchronous APIs for queries and through events for state changes.

**Chapter requirements.**
- Target Architecture contains one table, with exactly eight rows, one per service, with the columns Service, Data it owns, Owning team, Phase.
- Migration Phases describes exactly four phases, each as a subsection with a heading of the form "Phase N: Name", numbered 1 to 4, and assigns the eight services to them in the order above.
- Service-by-Service Plan has one subsection per service, using the service names above as the subsection headings, in the order above. For each: what moves, the data it takes over, its dependencies on the monolith and on other services, and its specific risks.
- Cut-Over and Rollback gives the rollback criteria as these two measurable triggers: an error rate above 1% for 5 minutes, or checkout p95 latency above 800 ms for 10 minutes. It also explains how traffic is shifted gradually (by percentage) through the routing layer.
- Organisation and Governance says who decides when a service is ready to take traffic, and how the release freeze before Christmas is handled.
- Risks and Mitigations: a table with exactly eight risks.

Do not repeat material between chapters; refer back to an earlier chapter instead.
