Write an architecture decision record, ADR-0007, on which message broker we should use for order events. It will live in our docs repository and should make sense to an engineer reading it in two years' time.

Context you need:
- We are Pellham Grocers' online-ordering platform: twelve services on one Kubernetes cluster in a single AWS region, run by a platform team of three.
- Order events (created, paid, picked, dispatched, delivered, cancelled) are currently passed by direct HTTP calls between services, which fails badly whenever one service is slow or down.
- Volume is about 300 events per second on average and 2,000 per second at the Saturday-morning peak, and is growing about 40 % a year.
- Four services consume every order event. The events for any one order must be processed in order.
- The analytics team needs to replay the last 7 days of events after a bug fix or when it builds a new report.
- One platform engineer has run Kafka in production before; nobody has run RabbitMQ.
- We would prefer not to add more than about $1,500 a month in infrastructure cost.

Compare exactly these three options:
1. Apache Kafka, self-hosted on our Kubernetes cluster.
2. RabbitMQ, self-hosted on our Kubernetes cluster.
3. Amazon SQS, with SNS for fan-out to the four consumers.

Structure the record under these headings: Status, Context, Options, Decision, Consequences. The status is Accepted, dated 4 March. Under Options, give each option its own subheading with its pros and its cons. The Decision should follow from the context, and Consequences should cover what gets easier and what gets harder, including the operational work we are signing up for. Keep it under 800 words.
