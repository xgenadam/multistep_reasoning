I lead the documentation team at Fernhill Software, which makes project-planning tools. Our docs are written by four technical writers and about forty engineers, and they read as if written by forty-four different people. I want a house style guide that everyone can learn in an afternoon and look things up in later. Please write it, about 6,500 words.

The readers are engineers who write docs occasionally and our technical writers. Be practical and persuasive: explain why each rule exists, so people follow it willingly, and show it in action. The guide should itself follow every rule it states (outside its "Bad" examples).

**Structure.** Use these sections, in this order, as the section headings:
1. How to Use This Guide
2. The Rules
3. Word List
4. Checklist Before You Publish

**The Rules.** Exactly these twenty rules, in this order, each as a subsection with the heading "Rule N: Title":

1. Write for the reader's task
2. Put the most important information first
3. Use the second person
4. Use the active voice
5. Use the present tense
6. Keep sentences short
7. One idea per paragraph
8. Use sentence-case headings
9. Use numbered lists for steps and bulleted lists for everything else
10. Start each step with a verb
11. Put the condition before the instruction
12. Name interface elements exactly and in bold
13. Define abbreviations on first use
14. Avoid Latin abbreviations
15. Say what will happen, not what "should" happen
16. Avoid words that judge difficulty, such as "simply", "just" and "easy"
17. Write numbers consistently
18. Write dates in an unambiguous format
19. Use inclusive, plain language
20. Make link text describe the destination

Each rule has, in this order: a one-sentence statement of the rule; a paragraph that starts "Why:" and gives the rationale; then one example pair, as two lines that start "Bad:" and "Good:", taken from realistic Fernhill documentation (task boards, Gantt charts, dependencies, resource planning, user permissions). Give each rule its own rationale; do not reuse the same justification across rules.

For rule 17, use these house conventions: spell out zero to nine and use digits from 10 upwards, except always use digits with units (5 MB, 3 days) and in tables. For rule 18, the house format is "23 October 2026" in text and "2026-10-23" in tables and code.

**Word List.** A table with the columns Use, Instead of, Note, with exactly these fifteen rows, in this order:
- sign in / log in, login (as a verb)
- select / click on, hit
- email / e-mail
- set up (verb), setup (noun) / setup (as a verb)
- because / since (for cause)
- for example / e.g.
- that is / i.e.
- and so on / etc.
- turn on, turn off / enable, disable (for user-facing switches)
- the Settings page / the settings screen, the config page
- dependency / predecessor link
- task board / kanban
- workspace / account (for a team's area)
- delete / remove (for permanent deletion)
- can / is able to

**Checklist Before You Publish.** Exactly ten checks, as a numbered list, each one line, that a writer runs through before publishing.

Do not add rules beyond the twenty, and do not repeat a rule's explanation in another section.
