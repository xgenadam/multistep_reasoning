Write a small package-dependency resolver in Python, as a package `resolve`: a version module, a package index, and a backtracking solver that prefers the newest versions and explains why resolution failed.

Layout:

```
resolve/__init__.py   re-exports Version, Range, PackageIndex, resolve, ResolutionError
resolve/versions.py   Version, Range
resolve/index.py      PackageIndex
resolve/solver.py     resolve, ResolutionError
```

## Versions (`resolve/versions.py`)

- `Version(text)` parses `MAJOR.MINOR.PATCH`: exactly three parts, each a non-negative integer written with digits only and no leading zeros (`0` is fine, `01` is not). Anything else raises `ValueError`. Versions are hashable, compare by `(major, minor, patch)` numerically (so `10.0.0 > 9.0.0`), and `str(v)` gives the canonical `MAJOR.MINOR.PATCH` text. Attributes `major`, `minor`, `patch`.
- `Range(spec)` parses a range: one or more constraints separated by commas, all of which must hold. Whitespace around constraints and operators is ignored. A constraint is one of:
  - `*`: any version;
  - `1.2.3` or `==1.2.3`: exactly that version;
  - `!=1.2.3`, `>1.2.3`, `>=1.2.3`, `<1.2.3`, `<=1.2.3`;
  - `^1.2.3`: at least `1.2.3` and below the next version that changes the leftmost non-zero part: `^1.2.3` is `>=1.2.3, <2.0.0`; `^0.2.3` is `>=0.2.3, <0.3.0`; `^0.0.3` is `>=0.0.3, <0.0.4`; `^0.0.0` is `>=0.0.0, <0.0.1`;
  - `~1.2.3`: `>=1.2.3, <1.3.0`.

  An empty spec, an empty constraint (as in `>=1.0.0,`), an unknown operator or a bad version raises `ValueError`. `v in r` and `r.contains(v)` test a `Version`. `str(r)` is the spec with all whitespace removed.

## Index (`resolve/index.py`)

- `PackageIndex()` starts empty.
- `add(name, version, requires=None)` adds a release. `version` is a version string; `requires` maps dependency names to range specs. Adding the same name and version twice raises `ValueError`, and so does a bad version or spec.
- `versions(name)` returns the list of known `Version`s of `name`, newest first (an empty list for an unknown name).
- `requirements(name, version)` returns a dict mapping each dependency name to its `Range`, for a `Version` that was added (`KeyError` otherwise).
- `PackageIndex.from_dict(data)` builds an index from `{name: {version: {dep: spec, ...}, ...}, ...}`.

## Solver (`resolve/solver.py`)

`resolve(index, requirements)` takes the root requirements as a dict of name → spec string (a bad spec raises `ValueError`) and returns a dict mapping every package it selected to its `Version`. It must give exactly the result of this depth-first search:

- The search keeps an *order*, a list of package names: initially the root requirement names sorted alphabetically. It also keeps the *selected* packages with their versions, in the order they were selected.
- At each step, the next package is the first name in the order that is not selected yet. If there is none, the search has succeeded and the selection is the result.
- The *constraints* on that package are the root requirement on it (if any) followed by the requirements on it of the selected packages, in selection order. Each constraint has a *requirer*: `<root>`, or the selected package written `name version` (`app 1.0.0`).
- Its candidates are its versions, newest first. A candidate is *acceptable* if every constraint contains it and, for every dependency of the candidate that is already selected, the selected version is in the dependency's range.
- For each acceptable candidate in turn: select it, append its dependency names that are not yet in the order to the order (in alphabetical order), and continue the search from there. If that continuation fails, undo the selection and the added names and try the next candidate. If no candidate leads to success (or there are none), this step fails, and the search goes back to the previous step's next candidate.

If the whole search fails, `resolve` raises `ResolutionError`, a subclass of `Exception` with attributes `package` (a name) and `explanation` (a string, also its `str()`). They describe the **first** step that found no acceptable candidate during the search: `package` is that step's package, and `explanation` is these lines joined with `"\n"` (no trailing newline):

1. `cannot resolve NAME`
2. one line per constraint on it, in constraint order: `  REQUIRER requires NAME RANGE`, where `RANGE` is `str()` of the range;
3. if it has no known versions, one line `  no versions of NAME are known`; otherwise one line per version, newest first: `  NAME VERSION is excluded by the constraints` if some constraint does not contain it, else `  NAME VERSION requires DEP RANGE, but DEP SELECTED is selected` for its first conflicting dependency in alphabetical order of dependency names.

For example, suppose the root requires `app` with `*` and `lib` with `>=2.0.0`, the only release of `app` is `1.0.0`, which requires `lib` `<2.0.0`, and the only release of `lib` is `2.0.0`. The order is `app`, `lib`. `app 1.0.0` is acceptable (`lib` is not selected yet), so it is selected; then `lib` has no acceptable candidate, there is nothing else to try, and the error's explanation is:

```
cannot resolve lib
  <root> requires lib >=2.0.0
  app 1.0.0 requires lib <2.0.0
  lib 2.0.0 is excluded by the constraints
```

Use only the Python 3.12 standard library. Give each file in its own fenced code block, with the file's path on the line just before the block.
