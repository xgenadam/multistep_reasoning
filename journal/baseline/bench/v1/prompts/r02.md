Write the postmortem for last Tuesday's outage of our shipment-tracking API. It goes to the whole engineering department and to the account managers of affected customers, so it has to be clear to readers who were not in the incident channel. The timeline below is the incident log, lightly cleaned up (all times UTC, all on the same day):

- 13:55 — A config change (PR #4471) is merged to the shared `services.yaml`. It was meant to set `db_pool_max: 20` for the new label-printing service, but the line landed under the `tracking-api` block, replacing the value 200. The PR was reviewed and approved by one engineer; the diff showed only the changed line, not the block it sat in.
- 14:02 — The deploy pipeline rolls the change out to all 24 tracking-api nodes at once. Config-only changes skip the canary stage.
- 14:07 — First customer-facing errors: HTTP 503 responses on `/v2/track`, error rate 3 %.
- 14:15 — Error rate reaches 18 %. Our largest retail customer's integration starts retrying aggressively, adding load.
- 14:19 — The alert "tracking-api 5xx > 5 % for 10 min" pages the on-call engineer, Priya Natarajan.
- 14:23 — Priya acknowledges, opens an incident channel and pulls in the database on-call engineer, Tomasz Wierzbicki.
- 14:31 — Suspecting database overload, Tomasz adds two read replicas. Database CPU is at 22 %; the error rate does not change.
- 14:40 — The status page is updated: "Degraded tracking API performance — investigating."
- 14:48 — Priya finds "connection pool exhausted (20/20)" in the application logs.
- 15:05 — Dana Okafor from the platform team links the pool size to PR #4471 through the deploy log.
- 15:12 — A revert PR is opened. The pipeline requires a second approver for changes to `services.yaml`; one is found at 15:24.
- 15:31 — The revert is live on all 24 nodes. The error rate drops to 2 % while the customers' retry backlog drains.
- 15:52 — The error rate is back below the 0.1 % baseline; the incident is declared resolved.
- 16:10 — The status page all-clear is posted.

Structure the postmortem under these headings: Summary, Timeline, Root cause, Action items.

- Open the Summary with three short lines giving the impact start, the impact end and the duration in minutes. Customer impact runs from the first customer-facing errors to the moment the error rate was back below baseline.
- Give the Timeline as a table with one row for every timestamp in the log above, no more and no fewer.
- In Root cause, explain the technical cause and the gaps that let it reach production and slowed recovery.
- Give exactly five action items as a numbered list. Each should be specific enough that someone could start on it tomorrow.

Keep it blameless: refer to people by their role (for example "the on-call engineer"), never by name, and focus on systems and process rather than individual mistakes. Aim for about 600-800 words.
