Write code review guidelines for the engineering team at Quillstack: 14 engineers working in a Python and TypeScript monorepo on GitHub, merging about 60 pull requests a week. The guidelines must reflect what we have already agreed:

- Pull requests stay under 400 changed lines; bigger changes are split, or reviewed together on a call.
- One approval is needed to merge; changes to the payments or auth packages need two.
- Reviewers respond within one working day, even if only to say when they will review.
- Formatting and lint are enforced in CI (black, ruff, prettier, eslint), so reviewers don't comment on style the tools already catch.
- Every review comment starts with its weight: "blocking:", "suggestion:" or "nit:".
- Only the author resolves a comment, and only after addressing it or replying to it.

Write exactly eight rules. Give each its own markdown heading in the form "Rule N: short title" (Rule 1 to Rule 8), then a one- or two-sentence rationale, then two short examples on their own lines labelled **Bad:** and **Good:** (a review comment, a PR description or a small code snippet). Finish with two sections, Reviewer checklist and Author checklist, each with exactly six items written as markdown checkboxes ("- [ ] ...").

The tone should be practical and friendly: this is for engineers who will use it every day, not a policy document. Aim for about 900-1,100 words.
