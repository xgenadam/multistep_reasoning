## What went right

- **Split work between agents.** At the user's request, two sub-agents ran in parallel: the generator launchers plus the watchdog, and the hidden-test runner. The agent kept the arm drivers and the config override, which share the run-file fields and the instructor seam. Both sub-agents' work was reviewed before commit: the watchdog and launcher diffs were read line by line.
- **Smoke test on a real server, kept out of the record.** It exercised the whole chain on qwen3.6-35b-a3b: arms, continuation, thinking in `reasoning_content`, extraction, the netns pytest sandbox and scoring. It found no tooling bug. It did confirm that the tests separate a real model bug (a1's `dict` subclass) from correct code.
- **The power check changed the plan before any authoring.** D-019's "≈ 47 decisive pairs" assumed the domains were pooled, which Q-8 forbids. The user chose 140 prompts (70/70) over 80 once they saw 60 % against 81 % power per domain.
- **The exemplar checklists were calibrated on real harness outputs from 0-16.** That exposed a strictness problem: a hard bound on "about 300–500 words". The fix became a writing rule.

## What went wrong

- **The first draft of the review note stated a Holm-corrected power, "about 70 %", without computing it.** The computed value is ≈ 60 % at Holm's strictest step. It was caught and corrected before commit. Numbers in notes are computed, never estimated in passing.
- **`arms.py`'s first version patched the harness's phase table at import time.** It was moved into `harness.py` itself before commit. Its first `plan_chains` also allowed branching chains, which would have recorded a shared parent twice; follow-up chains are now linear by rule.
- **The flash-next lane has no dry-run mode.** The launcher sub-agent faked one with a `docker` shim on PATH. It works, but it is clever code to maintain.

## Decisions

- **Bench v1 is 140 prompts, 70 per domain** (the user, 2026-10-23). It replaces "about 80" in Q-02 Scope and PLAN. This is a sizing refinement within D-019, not a new D entry.
- **Follow-up chains are linear (depth 1, one follow-up per root),** so every prompt's output is recorded once per arm and run.
- **Every arm samples at server defaults (no temperature),** as the pipeline does. This is recorded in run files and in the draft pre-registration.
- **Checklist items check only what a prompt states,** and "about N" widens by 10 %.
- **The pre-registration is a draft** (`design/Q-02-bench-v1.md` § 3). Nothing is in force until the user approves it.
