# New Synthesiser

## Current problem to solve
When combining the output of sub tasks, the synthesis tends to abbreviate, and misses some info out.
The current implementation is a rolling synthesis. Where the previous synthesis result, and the output of the latest sub task are fed to an llm, along with the original prompt, and instructed to join them together.

## Proposed solutions

### Patchwork quilt
What about the rolling update just appends to the output?
do we give it the output to date?
What about combining with the previous synthesis method, that keeps a running summary as it tends to be brief, then this method would take that input, and be told to **append** to a running output instead?
I feel like this could be a better solution than before, but I don't think its complete. The output of a later task could likely affect an earlier task!

#### pros
* simple

#### cons
* likely error prone

#### conclusion
A start in the right direction, but not complete


### document modification
The idea here is that we treat the final output as a document.
An editor agent would be responsible for integrating the output of sub tasks into the final document.

There are a few ways this could be achieved:
* via a diff approach similar to how cline handles updates in a file
  * could add logical divisions to reduce context size overhead
    * call them "chapters"
    * each chapter could have an autogenerated summary for efficient context size management.
    * initially keep it simple, start with single document, and how to update that document
* reading the entire document and then edditing it
  * isnt this essentially what we were doing before with rolling update synthesis, lets not do this!

This could be implemented in a similar manner to the Simple Synthesiser, but instead of full regeneration of existing, we follow the cline method:
* search and replace in the document
* entirely rewrite the document, but prompt in such a way that this is not preferred


#### pros
This seems like a more complete solution, after looking at cline its actually not

#### cons
could be a wild goose chase -- this works well in cline
could require additional work to keep within context size -- still true
could also be a rabbit hole, many ways to improve output!
