## Scope

Source: PLAN.md § Phase Q, D-007. This is a two-stage ticket.

**Stage 1, design (Fable 5.1 / high, plan mode):**
- **Ask the user first:** use Devstral-123B (`:8000`) as the judge beside
  Qwen, run sequentially, or accept self-judging (Qwen judging Qwen)? If
  self-judging, append its caveat to DECISIONS.
- The rubric(s) in `journal/baseline/rubrics/`.
- The pairwise protocol: both orders, ties = 0.5, an absolute rubric as
  secondary.
- The validation set:
  - 5 real pairs cut from the tracked run files, labelled by the user;
  - 5 plausible-but-wrong pairs (a missing requested section; an off-by-one
    in code).
- The judge budget (Q-4).
- Write the design into this ticket's Notes.

**Stage 2, implement (Opus 5.5 / medium):**
- `journal/baseline/quality.py`.
- `judge.base_url` (the harness `--judge-base-url` / `$JUDGE_BASE_URL`,
  recorded since O-03) plus a reachability check as step one.
- Win-rate + Wilson 95% CI.
- Judge calls never run inside a timing-gate window (Q-4). Claim the server
  in INDEX.

`needs_server` is behavioural because judging calls a model. No harness
turns are run.

  - **Two judge tiers** (the user's proposal, 2026-10-19; adopted as the
    design frame):
    - *Fast tier, co-resident.* The generator pinned to 2 cards, the judge
      on the other 2 (≤ 46 GiB). It runs G3 on the ~10-prompt subset (P7),
      Q-5 repeatability, rubric development and the Q-1 validation set.
      It needs a download, since nothing on disk fits.
    - *Slow tier, sequential.* The generator alone on 4 cards for the full
      campaign (`--jobs 3`; outputs and tokens stay clean), run files
      committed, then the big judge loaded alone marks every pair in one
      batch. It runs the Q-E1 verdict and the phase gates. The big judge
      also marks the fast tier's Q-1 set once, so both judges are scored
      against the user's labels on the same pairs. The generator in this
      tier may also be a bigger model, provided it has its own baseline
      (D-016: a backend without one cannot be gated).
    - A judge is fixed within a comparison: two judges' verdicts never
      share a win-rate table. Each verdict file records the judge backend
      and model, the rubric version and the run file it marked, and judging
      is a separate pass over committed run files (stage 2 builds it so).
  - **Recommended models.**
    - Fast judge (download, 2 cards): **Gemma 3 27B it**, Q6_K (≈ 22 GB) or
      Q8_0 (≈ 29 GB); 128K context; small KV cache (5:1 local/global
      attention); the strongest prose judge in its class, and not Qwen.
      Alternative: **Mistral Small 3.2 24B** or **Magistral Small 1.2**,
      Q6_K (≈ 20 GB), which keeps the fast judge in the slow judge's family.
      Cheap fallback: **gpt-oss-20b** (≈ 12 GB, one card, reasoning-effort
      knob), weaker. If a newer release of the same family in the 24–32B
      class exists, take it; this list reflects the model's knowledge, not
      a search.
    - Slow judge (on disk, 4 cards): **GLM-4.5-Air Q5_K_S** first
      (106B-A12B; ≈ 74 GB plus 6–12 GB KV at 64K; 12B active, so it marks
      fast; thinking mode), **Mistral-Medium-3.5-128B Q3_K_M** second
      (≈ 61 GB plus ≈ 12 GB KV at 64K q8_0; dense, slower, heavier quant).
      Devstral-2-123B (D-008's "future judge") is code-specialised, and P5
      moves code correctness to tests, so it ranks third. The Qwen3-235B
      quants are the generator's family and Q2, so they are out.
    - Self-judging stays the zero-setup fallback when no second model is
      loaded; its caveat goes to DECISIONS with the ruling.
  - **Judge context.** The 0-16 documents are small: 1–4 parts, 1.2–10.6K
    chars of body plus a 1.6–3K char summary, so a pair is ≈ 6–10K tokens.
    P6's long tasks push a pair to 30–60K, so the judge needs 64K context at

  - **Generator footprint when co-resident.** Per-call prompts in 0-16 peak
