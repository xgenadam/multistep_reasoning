## Scope v1 (2026-10-15)

Phase 0 item 5: one extra composer call **after the final sub-task**,
scoped to outline-level cleanup (merge/delete redundancies). This is the
explicit "revise before presenting" step the design promises but only
applies between sub-tasks today.

- Input to the consolidation call: outline + previews **only**, never part
  bodies (token cost stays bounded by part count, not content length).
- Ops it may emit: `merge_parts`, `delete_part`, `move_part` — never
  `add_part` (no new content; that is a composer job, not a cleanup job).
- **Must be latency-budgeted**: adds ≤ 1.5× a single compose call's p50
  wall time to the total turn, and total tokens per turn grow ≤ 25% vs. the
  pre-consolidation baseline (S-002, recorded 2026-10-15 in
  `journal/baseline/runs/`).

**Implementation landed (in_progress, commit acc83a7):**
- `DocumentComposer.consolidate(user_request, document)`: one best-effort
  pass, outline + rolling summary only (no part bodies), restricted op
  union `merge_parts | move_part | delete_part` (schema rejects add_part and
  all body-editing ops). Best-effort: a proposal that empties the document,
  references a missing id, or fails apply is logged and abandoned — the
  pass can never break the pipeline or drop unverifiable content. No-op
  when < 2 parts.
- `OptionsConfig.consolidation: bool = False` — **off by default** so it
  cannot perturb the baseline or the 0-04/0-05 verification. Harness gains
  `--consolidation` to flip it; `classify_call` gains a `consolidate` label
  (its restricted schema carries no add_part, so the system-scan misses it —
  classified by its unique user-prompt signature).
- Orchestrator hook runs it after the final sub-task, before `done`, reusing
  the existing summary-update branch (oracle or rolling).
- 8 new unit tests (composer unit + orchestrator on/off hook). Suite
  **186 passed / 10 skipped / 0 failed**.

**Measurement plan (A/B on s4, the P0-4 anchor scenario):** s4 ends
multi-part (3 sections, 2-3 sub-tasks) — unlike the s1/s2/s3 post-merge
runs, which all converge to a single part before the hook, so s4 is where
the consolidation call actually fires. Two sequential harness runs:
`--scenario s4_anchors --runs 1` (default) then the same with
`--consolidation`. Compare: (a) the `consolidate`-kind call's wall time
vs compose p50 (budget ≤ 1.5× ≈ 20–27 s against the 13–18 s p50); (b)
per-turn token totals, B vs A (budget ≤ 25%; also report both vs the
pre-consolidation anchor 44.8K/36.0K prompt, S-002); (c) behavioral —
the ops must be outline-sane (merge/move/delete, no content loss, no
rebuilt bodies).

**Why NOT the s3 t1 rebuild churn:** the hook runs after the final
sub-task's compose, at which point the s3 t1 document has already been
rebuilt into a single part — `consolidate()` is a no-op on < 2 parts.
The rebuild is compose-time behavior (final sub-task's op set), not
end-of-turn redundancy, so it is out of this ticket's reach; it is
recorded in S-002 as the residual 0-04/0-05 finding. Consolidation's
real role is second-chance cleanup when compose leaves overlapping parts
at the end (defensive; the 0-04 dedupe rule means this is the minority
case).
