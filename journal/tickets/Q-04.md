## Scope

Source: PLAN.md § Phase Q (Q-04, Q-10); Q-01 Notes 2026-10-19 (the two
judge tiers and the candidate list); the user's request of 2026-10-19 that
the judges be chosen by comparison, not by reputation. Q-01 stage 2 proves
`quality.py` on one judge; this ticket runs the same set across candidates.

**Set.** The Q-1 validation set as Q-01 stage 1 fixes it: 5 real pairs cut
from the tracked run files and labelled by the user, 5 plausible-but-wrong
pairs, and 2 padded-but-not-better pairs (P5). Every pair in both orders,
and every pair/order twice (Q-5): 12 pairs × 2 orders × 2 repeats = 48
calls per judge. Every judge sees the same prompts and the same rubric
version.

**Candidates.** Two tiers (Q-01 Notes 2026-10-19). Self-judging, the
generator judging its own output, runs in both tiers as the control.
- *Fast tier* (co-resident with the generator; one card, ≤ ~20 GB with KV,
  until the user's three-card experiment on flash-next frees more):
  gpt-oss-20b; Gemma 3 27B it Q4_K_M; Mistral Small 3.2 24B or Magistral
  Small 1.2 Q4_K_M; Qwen3.6-35B-A3B Q4_K_M (on disk; the same-family
  control). Downloads are the user's call. A candidate not on disk by the
  run is recorded as skipped, not failed.
- *Slow tier* (sequential; the generator unloaded, the judge alone on four
  cards): GLM-4.5-Air Q5_K_S; Mistral-Medium-3.5-128B Q3_K_M;
  Devstral-2-123B Q3_K_M; Qwen3-235B-A22B UD-Q2_K_XL (the same-family
  control). All on disk.

**Per judge and tier, record:**
- agreement with the user's labels on the 5 real pairs;
- the correct side on the 5 wrong pairs, in both orders;
- position consistency: the share of pairs with the same verdict in both
  orders;
- length bias: the padded pairs, both orders;
- repeatability (Q-5): agreement between the two repeats, same pair and
  order;
- the tie rate;
- cost: prompt and completion tokens and seconds per call; for the slow
  tier also the judge's load time and VRAM (the swap cost).

**Selection rule, fixed here before the run.** In each tier, the judge
that meets Q-1 (≥ 4/5 on the real pairs and ≥ 4/5 on the wrong pairs, in
both orders) and Q-5 (≥ 90 %) with the highest position-consistent label
agreement wins; ties go to the cheaper judge per pair. If no fast-tier
candidate meets Q-1, the fast tier runs on self-judging under its DECISIONS
caveat, and G3 between campaigns is advisory until a passing judge exists.
If self-judging ties or beats the best cross-family judge in a tier, that
is reported as found.

**Output.** One table in Measurements, a row per judge and tier; the
verdict files under `journal/baseline/runs/`; and a DECISIONS entry naming
the fast and slow judges with their recorded cost per pair (the Q-4
budget).

The user operates every model swap and download. Claim the server in INDEX
for each judge window. Judge calls never run inside a timing-gate window
(Q-4).

## Notes

- 2026-10-19 (instantiated by Q-01 stage 1 at the user's request): the user
  wants the fast and slow judges chosen by comparison. The fast tier waits
  on the user's experiment to fit flash-next on three cards; the slow tier
  needs only a model swap. Candidate sizes (estimates) are in Q-01 Notes
  2026-10-19.
- 2026-10-19 (the user's two follow-ups):
  - **The three-card experiment is not needed yet.** Q-01 stage 1 needs no
    server; Q-01 stage 2 validates the tool on whichever judge is up, and
    self-judging on `:8091` needs no swap; the Q-02 campaign runs the
    generator alone; its judging is a slow-tier swap. The fast tier earns
    its card at Q-03, when G3 wants a judge between code changes. If the
    slow tier's recorded load time makes a swap per G3 run acceptable, the
    fast tier can be dropped instead. A three-card generator is a new
    backend for wall time (D-016): it needs its own baseline before any
    timing gate runs on it. Token and op counts stay comparable.
  - **Each judge is served from its own endpoint**, with its own server
    software and model name; none shares `:8091`. `quality.py` therefore
    takes the judge's base URL and model name per candidate
    (`--judge-base-url` and a `--judge-model`, D-008: no silent default),
    checks reachability first, and writes both into every verdict file.
    vLLM 404s on a wrong model name; llama.cpp servers ignore it.
