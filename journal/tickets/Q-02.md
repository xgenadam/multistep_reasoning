## Scope

Source: PLAN.md § Phase Q, D-007, D-019; `journal/design/Q-01-judge.md`
§ 1 and § 9. This answers the README's open question: does the harness
improve responses over a single model given the same compute? The answer
is recorded whatever it is, and it is the re-plan point before A-03.

**Generators (D-020, 2026-10-23):** flash-next (vLLM, `:8090` in the
agent container), Qwen3.8-27B UD-Q6_K and Qwen3.6-35B-A3B UD-Q4_K_M
(llama.cpp, from `~/models`). Every arm runs on every generator; each
generator's (b) vs (a″) claim is pre-registered and tested on its own; the
gains are compared descriptively only. The two llama.cpp generators each
get a 0-16-style baseline (s1–s4 × 2, `--jobs 1`) before any wall-time
comparison. Judges (D-021, superseding D-020's judge sentence):
flash-next is the judge of record for every table; Devstral-2-123B
(tensor split) judges every generator's (b) vs (a″) pairs as the
concurrence judge, and a claim passes only if both favour the same arm.
Judge calls run on a server with prefix caching off (flash-next: the
tuned lane, not the prefix lane); with it on, repeats flip (Q-04 Notes). Design: `journal/design/Q-02-model-size.md`.

**Arms**, same prompt, model and per-call `max_tokens`, per generator:
- (a) a single call, thinking off;
- (a′) a single call, thinking on;
- (a″) self-refine: draft → critique → revise for N rounds, N tuned on a
  5-prompt pilot per domain so the median completion tokens per prompt are
  within ±25 % of the harness's (≈ 6.4 K on `:8091`, 0-16); reasoning
  tokens count;
- (b) the harness;
- (c) the harness + consolidation, on the overlap subset only (follow-up
  turns and prompts with deliberately overlapping deliverables; see the
  S-013 note below).

Single-model arms continue until done on long prompts: on
`finish_reason: length` the driver sends "continue", at most 3 times.

**Primary comparison:** (b) against (a″), pre-registered in Notes before
the first run file: the effect (default 0.70 on decisive pairs), n and the
analysis (Q-6). (a) and (a′) are secondary. Claims follow D-019.

**Scoring:** code prompts by hidden tests (pass-rate with a Wilson CI; the
judge only when both arms' tests agree); report prompts by checklist, then
the judge; domains never pooled (Q-8).

**The set:** `journal/baseline/bench/v1/` (Q-9): `prompts/<id>.md`,
`tests/<id>/`, `checklists/<id>.yaml`, `manifest.yaml` with domain, long,
follow-up and overlap flags; ≥ ⅓ long (deliverable beyond one call's
`max_tokens`, or multi-file) and ≥ 20 % follow-ups; a `g3` subset of ≈ 10
(half code, half report, two follow-ups); `std-*` slices the user downloads
(design note § 9). 140 prompts, 70 per domain (the user, 2026-10-23; was
"about 80"): domains are never pooled, so each domain needs its own ≈ 47
decisive pairs for D-019's 80 % power at 0.70.

**Stages, one per session:**
- Stage 0 (Opus 5.5 / high): bench v1; the arm drivers (`arms.py`); a
  harness config-override flag for the arms and for Q-05's ablations; the
  hidden-test runner (file parts to a temp dir, pytest with a timeout);
  the commit hash in run files; wall-clock time per call, per prompt and
  per arm in every driver (D-019 addendum).
- Stage 1 (Sonnet 5.5 / low): the campaign at `--jobs 3`, from a pinned
  worktree at the recorded commit, run files committed as they land, the
  server claimed in INDEX. An A-02 session may run meanwhile on master.
- Judging: one claimed slow-tier window on the committed run files
  (`quality.py` with the judge Q-04 chose; self-judging only as the
  fallback with its caveat), resumable from the verdict file.
- Stage 2 (Opus 5.5 / high): win-rate and CI per pairing, tokens, wall and
  length per arm, the pre-registered test, the G3 inputs for Q-03. If the
  harness loses, the re-plan is a Fable 5.1 / high session; say so in the
  Handoff.

Cost estimate: generation ≈ 5–7 h at `--jobs 3` for flash-next, less for
the faster two; judging 10–18 h of slow-tier windows per generator
(design note § 5), so up to about 30–54 h for three unless Q-04's judge
or row split is faster. Stage 0 re-estimates it from measured rates.

  - **Config override:** `apply_overrides` in `config/loader.py` sets
    `section.key=value` on any `OrchestratorConfig` field (values parse as
    YAML) and rejects unknown paths, which pydantic alone would ignore. The
    harness takes `--set` (repeatable), and its run file now records
    `commit`, `dirty`, the resolved `config` and the `overrides`.
  - **`arms.py`:** `run` / `plan` / `match`. Arms `a`, `a1`, `a2`, `b`, `c`
    map to (a), (a′), (a″), (b), (c). Every arm gets the same prompt, the
    served model and `max_tokens` 8192, and no temperature is sent, so
    every arm samples at server defaults, as the pipeline does.
    - Single-model calls continue on `length` up to 3 times.
    - Follow-ups run as linear chains in one job: the harness continues the
      Document; single-model arms get the parent exchange as history.
    - The run file is rewritten after every chain, and `--resume` re-runs
      any chain that did not finish whole.
    - Wall time per call, per prompt and per arm (`arm_elapsed_seconds`).
    - The self-refine prompts are versioned (`arms-v1`) and belong to the
      pre-registration.
    - `match` reports each arm's median completion tokens per prompt
      against (b)'s, the ±25 % check, and the N the pilot's per-call
      medians predict.
  - **`hidden_tests.py`** (sub-agent): `score RUN_FILE` and `check-bench`.

    - pytest runs in a temp dir under `unshare -rn` (no network), with a
      fixed config and a whole-run timeout; only the hidden tests are
      collected.
    - `check-bench` requires each reference to pass, an empty deliverable
