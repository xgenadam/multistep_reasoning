     left in a fresh run.

     `--jobs > 1` they include calls from concurrent turns (≈ :335-363).
   - Add a turn-id ContextVar per scenario thread and attribute each call to
     its turn.
   - The thread pool must propagate context (`contextvars.copy_context()`
     per job).
3. **N15, streamed usage.**

   - If llama.cpp omits usage, record `usage: null` and count the streamed

## Notes

- 2026-10-19 (S-008, Opus 5.5 / high, as specified). Everything in Scope
  1–8 landed in one commit. No server was used.
- **Labels (N13).** The orchestrator's status events are coarser than the
  seven kinds: "Decomposing…" covers both decompose and critique, and
  "Executing i/n" covers both executor rounds and oracle asks. The existing
  `progress.llm_step` label (set before every pipeline call) splits them.
  The harness now opens a `live_session()` per turn and reads that label at
  the seam. Mapping: `PHASE_KINDS` + `STEP_KINDS` in `harness.py`. The
  keyword classifier only runs for calls outside a known phase (the legacy
  synthesiser, setup); each call records `label_source`.
- **The recorded data confirms N13 exactly.** On every legacy turn in the
  ten tracked files, keyword `summary` = the executor-phase call count, and
  `system_other` = summary-phase calls + 1 critique. compose, consolidate
  and decompose (+1 critique) agree with the phase counts
  (`test_rescore_tracked_runs.py`).
- **Two attribution holes beyond the ticket:**
  - A call whose `create()` raised bumped the counter but left no record.
    It is now recorded with `error`, in its turn.
  - A turn that raised lost its calls with the scenario record. The partial
    turn (`error`, `llm`) is now kept, and `run_scenario` returns the record
    with `error` instead of raising.

  An unreachable-endpoint smoke run (scratchpad, not tracked) shows
  `attribution: exact`, with 5/5 calls labelled `decompose`.
- **instructor retries a 400 five times.** `get_streamed_json_response`
  defaults to `max_retries=5`, so one executor round against a failing
  server is 5 calls, all now counted (`calls_raised`). This is behaviour,
  not a harness defect; noted for 0-12/0-13.
- **Statuses (N16).** `TaskStatus` has no partial value, and a failed
  sub-task leaves no executor-history entry. The harness therefore wraps
  `execute_one` per turn:
  - raise → `failed`;
  - history flags `budget_exhausted` → `budget_exhausted`;
  - otherwise `str(sub_task.status)`.

  The pipeline itself is unchanged; N4 stays with 0-12.
- **Streamed usage (N15).** The `include_usage` chunk has empty `choices`.
  The pipeline indexes `choices[0]`, so the harness swallows that chunk (it
  already skipped choice-less chunks). `tokens_partial` counts only calls
  that *answered* without usage; raised calls are `calls_raised`.
- **check.py (N17).** The P0-1/P0-2/P0-3 expectations are new keys in
  `scenarios.py`: `section_parts_max: 0`, `file_parts_max: 0`,
  `followup_merge_or_patch`.
  - P0-3 reads this turn's ops. The op log is cumulative, so the harness
    now writes `turn_op_counts`, and legacy files subtract the prior turn's
    `op_counts`. The result matches a raw op-log slice on every s3 file.
  - "Patch" = `replace_in_part`, `insert_in_part`, `append_to_part` or
    `update_part`.
  - A check that cannot apply reports `n/a` and fails nothing.
- **Finding: P0-3 op evidence fails on two tracked follow-ups.** These are
  `182246Z` s3 t1 (the run 0-04 was closed on) and `165827Z` r1 t1. Each
  t1 is add ×3 → delete ×3 (→ re-add): the rebuild churn S-002 described,
  which the Jaccard check passed vacuously on a one-part document. 0-04 is
  not reopened here. The next s3 run (0-16) scores it with the new check.
- **compare.py.**
  - G2 is the marginal tokens ÷ the B turn total, from per-kind and
    per-phase token sums. The triggered summary is the
    `Updating summary after consolidation` phase.
  - Legacy files have no per-kind tokens, so G2 reports `UNMEASURABLE`,
    which counts as a failure (exit 1, not a pass).
  - B-vs-A growth is still printed, but not gated.
  - The contamination yardstick is `CLEAN_COMPOSE_P50_S = 18.0`, the upper
    end of S-002's 13–18 s.
  - A warning prints when A and B ran on different endpoints.
- **Per-run timing verdict.** 0-16 needs "the contamination check accepts
  every run", but `compare.py` only gates a pair. So `check.py` now prints
  `timing: clean | CONTAMINATED` per turn, using `compare.contamination` (one
  rule, one constant). It is reported, not scored.
  - Against the hand calls in S-002/S-003, the rule agrees on post-merge
    (4/4 flagged), on both 0-06 arms, on the `jobs=3` smoke run and on the
    S-002 baseline (6/6 clean).
  - It flags both `152027Z` follow-up turns, which S-002 treated as clean:
    their compose sees a grown document (p50 48.2 / 24.1 s).
  - It misses `165827Z` r0 t0, which S-002 called contaminated from wall
    time, because compose p50 was 18.1 s.
  - So the compose-only proxy fits single-turn anchors (compare.py's s4
    gate) and is coarse on follow-up turns. A per-scenario/turn yardstick
    is 0-16's call.
- **Run files** now carry a per-turn `calls` list (every CallRecord), so
  later re-scoring does not depend on the aggregates. It adds a few KB per
  turn. Each also carries a run-level `attribution` block (global vs
  in-turn totals), which `check.py` verifies.
