## Scope

Source: PLAN.md § Phase 0 close-out, N18, D-007. This is a two-stage ticket,
one stage per session.

**Stage 1, run (Sonnet 5.5 / low):**
- Run s1–s4 × 2 with `--jobs 1` on post-0-14 labels, in a genuinely idle
  window. Claim the server in INDEX before starting and release it after.
  The session must not call the model while the run is going: start it in
  the background and wait for it.
- `--label rebaseline-0-16`.
- `compare.py`'s contamination check must accept every run; a rejected run
  is redone.
- Commit the run file(s) with a dated Notes bullet.

**Stage 2, analyse (Opus 5.5 / high):**
- New denominators per scenario: wall time, compose p50, decompose-pair
  p50, executor-turn p50, and prompt/completion tokens per turn.
- They replace AGENTS.md § Baseline, and INDEX gets a one-line pointer.
- Attribute the prompt-token growth since S-002 (post-0-04/0-05 runs at
  265–432 K per turn vs a pre-change median ≈ 80 K) by call kind. Candidates
  are composer `need_part_ids` fetches, extra oracle rounds and
  regeneration.
- Decide fix-or-accept and append the decision to DECISIONS.md.
  - A fix that is a prompt redesign is its own ticket; its design runs on
    Fable / high.
  - If the fix lands before A, re-baseline again (D-007).

- 2026-10-19 (S-011, stage 2, no server, no model calls): analysis of the S-010 run file.
  - **N18 does not reproduce.** On current code, prompt tokens per turn run
    29.6–100.0 K (median 54.5 K), under the pre-change ≈ 80 K median. The prompt
    text barely changed after 0-05 (`git diff 646b070 HEAD`: 0-09's fence rule).
  - **The Oct-15 totals are not prompt sizes.** Divide each Oct-15 turn's
    prompt tokens by its non-streamed calls (pre-0-14 streamed calls recorded
    no usage, N15). The turns fall into two modes:
    - a plausible mode at 4.0–9.6 K per call;
    - an inflated mode at 18–44 K per call: S-002's own s1 r0 (30.5 K) and
      s3 r0 t1 (28.0 K), then every run from 16:58 on.

    `cap_prompt` holds compose and decompose to 16,384 tokens plus instructor's
    system schema (≤ 2.3 K). Executor round 2 is ≤ ≈ 21 K (budget/4
    observations), and the Oct-15 loops ran about 2 rounds. So no call could
    average 30–44 K. The inflation predates 0-04/0-05, so it is not their doing.
    Its mechanism on `:5000` (llama-server) is unverified, because the 27B is
    not loaded. The largest single call here is 8,979.
  - **Static growth since S-002** (cl100k, the same script on `git archive`
    of `3f698d2`, `646b070` and HEAD):
    - 0-04/0-05 add about 1.19 K per compose call: the template +403 and the
      `ComposerResponse` schema +392, sent twice;
    - 0-09 adds +77;
    - executor and decompose are unchanged.

    That is about +4–5 K per turn, or ≈ +8 % of the new median.
  - **Where prompt tokens go now** (807,337 total):

    | Call kind | Share of prompt tokens |
    | --- | --- |
    | compose, first call per sub-task (50) | 42.8 % |
    | compose, extra calls (12; `need_part_ids` fetches or apply retries, which the run file cannot tell apart) | 11.6 % |
    | executor round 1 (50) | 17.9 % |
    | executor rounds 2+ (31; extra oracle rounds) | 14.7 % |
    | decompose, initial (14) | 5.4 % |
    | decompose, regeneration (5) | 2.2 % |
    | critique (14) | 1.3 % |
    | summary (50) | 4.1 % |
    | oracle (1) | 0.1 % |

    The ticket's three candidates (extra compose calls, extra oracle rounds,
    regeneration) together account for about 28.5 %, and none is a multiplier.
    Compose sends about 7 K prompt tokens for a 92-token median reply.
  - **The schema is sent twice on every JSON call.** It goes in the prompt
    (`model_json_schema(), indent=2`; indent=4 for decompose) and again in the
    system message that instructor's JSON mode adds. Per call (cl100k):

    | Call kind | Schema tokens per call (system + prompt) |
    | --- | --- |
    | compose | 2,236 + 2,167 |
    | executor | 978 + 910 |
    | decompose | 1,338 + 1,448 |

    The per-kind minimum prompts fit this overhead: compose 6,452, decompose
    3,085, executor 2,494. Schema text is about 59 % of all prompt tokens, and
    the duplicate copy is about 29 %. This is now N21 (D-016).
  - Every turn ran the critique, including the 13 turns with ≥ 3 final sub-tasks
    (0-10a's N2).
  - **Yardstick.** `compare.CLEAN_COMPOSE_P50_S` is now keyed by run-file
    `backend`:
    - `:8091` = 2.23 s, the pooled p50 of 62 compose calls; the limit is 2.90 s;
    - `:5000` = 18.0 s, S-002's number, labelled stale;
    - any other backend counts as contaminated, because it has no yardstick.

    One yardstick serves every scenario. Per-turn p50s are 2.00–2.60 s, s3
    follow-ups included, so the s3 noise 0-14 warned about does not appear on
    this generator. `check.py` marks 14/14 turns clean, and the Oct-15 `:5000`
    verdicts are unchanged.
    `tests/test_baseline/test_compare_gates.py` covers each backend's limit
    and the unknown-backend case. `make test`: 271 passed, 10 skipped.
  - **A-6 has no usable denominator.** The baseline made one oracle call
    (1.34 s, 529 prompt tokens), so the A-6 baseline cannot come from P0-7.
    A-05 must measure the pre-A oracle itself (handoff bullet in A-05).
