## Scope

Found during 0-05's 3× P0-1 verification (`20261015T182246Z_post-merge-0.04`
s1 + `20261015T190302Z_0-05-x2x3` s1b/s1c): the composer wraps code in
```fences inside the file part's body, but `Document.render()`
(models.py:101-105, mode `markdown_with_files`) ALREADY wraps file parts in
a fence with language inferred from the title (`_fence_language`,
models.py:153). The rendered output is therefore:

    ## wordcount.py

    ```py
    ```python
    #!/usr/bin/env python3
    ...
    ```

The outer `py` fence (language inferred from the `.py` extension) closes at
the first line of the model's own fence, so the rendered markdown is
malformed: a one-word empty code block followed by stray text. 2/3 of the
verified runs (s1, s1b) additionally carry a verification table/notes block
after the closing fence — also outside the intended code block.

## Notes

- Fix of record: prompt-side. COMPOSE_PROMPT rule 7 must say a file part's
  body is RAW file content — never wrap in ``` fences (rendering fences it,
  inferring the language from the title), and no trailing commentary/tables
  in a code part (put notes in a separate section part if needed).
- Do NOT strip fences in render() as the fix: a file part may legitimately
  contain fenced content inside (e.g. a README with embedded code); only the
  model's outer wrapper is the defect, and teaching the model is cheaper than
  guessing which fence is the wrapper.
- Regression check: render the three run file parts, assert no
  consecutive ` ``` ` at the start of the fenced block and that the body
  does not begin with a fence. Cheap to add to check.py as an s1-family
  assertion (`file_part_body_starts_with_fence` must be absent).
- Criteria: none assigned (defect ticket; verified by re-rendering the run
  artifacts + a harness s1 re-run showing a clean fence). Not gating any
  P0-1 pass/fail — the gate itself passed; this is a rendering-quality bug.
