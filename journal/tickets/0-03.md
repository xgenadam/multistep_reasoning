## Scope

Phase 0 item 2 / defect D3: the op set (`operations.py`) has
`add_part, append_to_part, replace_in_part, insert_in_part, update_part,
move_part, delete_part` but no way to **merge** — so the composer's only
dedupe tool is delete-and-re-add, which loses provenance and op-log
integrity. Add a `merge_parts` op:

- Schema: `{id, kind, title?, ids: [source ids], after}`.
- Semantics: concatenate source bodies **verbatim** in the given order,
  insert the new part, delete the sources.
- Implementation: schema model + `_apply_one` case in
  `document/apply.py` (alongside the existing ops at operations.py:66-72).
- **Unit tests are in scope here** (pure state manipulation; the phase gate
  is still behavioral): happy path, empty ids list, id not found, source
  appears twice in ids, `assert_payload_kept` interaction (a merge dropping
  the current sub-task's result must still raise).
- `changed_part_ids` already feeds deleted ids into the summary update —
  verify the merge path exercises that (see 0-07).

This op unblocks Phase P's snapshot design (merge semantics the DAG
frontier needs) and is the primary tool for the P0-3 dedupe rule.

## Notes

- Gated by: 0-02 not required (independent), but 0-04's prompt work
  references this op, so land 0-03 first.
- **Schema deviation (decided 2026-10-15):** the scope sketched
  `{id, kind, title?, ids, after}` (a *new* part). Implemented instead as
  `{ids: [source ids], min_length=2, unique}` with **in-place survivor
  semantics**: the first `ids` entry is primary — its id/kind/title/
  origin_task survive, it stays at its original position, body =
  all `ids` bodies joined `"\n\n"` in `ids` order; the rest are deleted
  (highest index first so positions stay valid). Rationale: the two
  consumers (dedupe, the consolidation pass) both want "fold these into
  the one that should live", not "create a fresh part and re-place it";
  in-place keeps provenance, needs no `after` bookkeeping, and makes a
  `merge_parts` no longer shadowable by a stale `add_part` id. Ordering /
  survivor choice is fully expressible via `ids` order. If a future use
  needs "new merged part with a fresh identity", that is add_part +
  body_source-less copy — out of scope.

## Measurements

- **Unit tests: 10 new, all pass** (`tests/test_document/test_apply.py`):
  content preserved + primary kept; ids-order reordering; primary metadata
  (id/kind/title/origin_task) kept; atomic on unknown id; untargeted parts
  keep object identity; duplicate-ids rejected; single-id rejected;
  patch-only integrity interaction (`assert_payload_kept` passes without a
  payload); op_log records `merge_parts` + origin_task;
  `changed_part_ids` returns survivor + all absorbed ids (feeds summary
  update + part re-attachment).
- Full suite: **8 failed (same pre-existing 8, now 0-08's), 164 passed,
  10 skipped** — zero new failures from the op.
- P0-3 dedupe *rate* is NOT measured here: that is behavioral, needs the
  composer to actually use the op (0-04) and a re-run against the S-002
  baseline. The unit gate proves the op is sound; the rate gate lands in
  0-04/0-06.
- `changed_part_ids` extended (composer.py) so a merge reports survivor +
  sources; previously it keyed off `op.id` which a merge lacks — would
  have silently skipped the summary update.
